# ТЗ фронтенда: среда моделирования распределённых транзакций

Версия от 18.11.2026

## 1 Общие сведения

Фронтенд — веб-приложение с визуальным холстом. На холсте пользователь собирает микросервисную систему, запускает её модель под нагрузкой и видит, как поведение системы зависит от архитектурных решений и паттернов распределённых транзакций.

- **Тема диплома:** «Разработка среды моделирования для сравнительного анализа паттернов распределённых транзакций в микросервисных системах».
- **Состав системы:** фронтенд (этот документ) и движок имитационного моделирования на Go (отдельное ТЗ). Фронтенд не выполняет моделирование сам: он редактирует схему, передаёт её движку и отображает поток событий и метрик.
- **Статус:** черновик. Подход (имитационная модель или реальные сервисы) ещё согласовывается с руководителем. ТЗ написано в предположении имитационной модели; при смене подхода затрагиваются в основном разделы 5.6–5.8 и 6.

### Цели фронтенда

1. Дать наглядный способ собрать архитектуру из типовых элементов без кода.
2. Показать в динамике последствия решений: перегрузку, рост задержек, отказы, аномалии согласованности.
3. Дать сравнить паттерны распределённых транзакций на одной схеме, нагрузке и сценарии отказов.

## 2 Пользователи и сценарии

У системы два типа пользователей. Регистрация и роли не нужны: оба работают в одном интерфейсе.

| Пользователь | Что ему нужно |
| --- | --- |
| Обучающийся (студент, начинающий разработчик) | Собрать систему из шаблона или с нуля, запустить, увидеть проблему, получить подсказку, исправить архитектуру и увидеть эффект |
| Исследователь (автор диплома, преподаватель) | Задать одну схему и сценарий, прогнать её с разными паттернами и сидами, получить сравнительный отчёт и выгрузить данные |

### Ключевые сценарии

1. **«База не вытягивает».** Пользователь собирает клиент → сервис → БД и поднимает нагрузку. Узел БД краснеет, p99 растёт, появляется подсказка. Пользователь нажимает «Шардировать», и метрики нормализуются.
2. **«Шарды ломают транзакцию».** После шардирования операция затрагивает два шарда. Интерфейс предупреждает, что локальная транзакция больше не гарантирует атомарность, и предлагает выбрать паттерн.
3. **«Урони координатор».** Во время работы 2PC пользователь отключает координатор. На холсте видны зависшие блокировки у участников и рост задержек.
4. **«Дубли сообщений».** В хореографической саге включается дублирование доставки. Без идемпотентности растёт счётчик нарушений инварианта «деньги списаны один раз».
5. **Сравнение.** Исследователь выбирает схему, 2–5 паттернов, уровни нагрузки и сценарий отказов, запускает пакетный прогон и получает отчёт с графиками.

## 3 Технологический стек

Основа — React + TypeScript, холст на React Flow: эта библиотека даёт узловой редактор из коробки, и не придётся писать холст с нуля.

| Задача | Технология | Почему |
| --- | --- | --- |
| Язык и фреймворк | TypeScript, React | Стандарт для сложных интерфейсов, типы защищают контракт с движком |
| Сборка | Vite | Быстрая сборка и горячая перезагрузка |
| Холст | React Flow (xyflow) | Перетаскивание, связи, масштаб, мини-карта, кастомные узлы |
| Анимация запросов | Слой Canvas 2D поверх холста | Сотни движущихся точек без нагрузки на DOM |
| Состояние | Zustand | Простое хранилище, рекомендуется самим React Flow |
| Графики | Apache ECharts | Живые обновления, гистограммы, диаграммы Ганта для трассировки |
| UI-компоненты | shadcn/ui + Tailwind CSS | Готовые формы, диалоги, вкладки; светлая и тёмная темы |
| Связь с движком | REST (fetch) + WebSocket | Схемы и отчёты по REST, ход симуляции потоком через WebSocket |
| Валидация схемы | Zod | Проверка импортируемых JSON-проектов и сообщений движка |
| Тесты | Vitest, Playwright | Юнит-тесты логики и e2e-сценарии из раздела 2 |

Типы схемы и событий желательно генерировать из единого описания (JSON Schema или OpenAPI), чтобы фронтенд и Go-движок не расходились.

## 4 Структура интерфейса

Вся работа идёт на одном главном экране с холстом; стартовый экран и экран сравнения вспомогательные.

Раскладка главного экрана:

- **Верхняя панель** (во всю ширину): проект · Старт / Пауза / Стоп · скорость · виртуальное время · seed · Сравнить · Экспорт.
- **Палитра** (слева): клиент, API Gateway, балансировщик, сервис, база данных, кэш, брокер сообщений.
- **Холст** (в центре): узлы перетаскиваются из палитры и соединяются; цвет и бейджи показывают нагрузку, точки — запросы; подсказка появляется рядом с проблемным узлом.
- **Панель свойств** (справа): параметры, эндпоинты (шаги и паттерн), метрики узла; для БД — кнопки «Шардировать», «Реплицировать», «Партиционировать».
- **Нижняя панель** (во всю ширину): вкладки «Метрики», «Трассировка», «Журнал событий», «Задания».

Боковые и нижняя панели сворачиваются и меняют размер, чтобы освободить место под холст.

| Экран | Содержание |
| --- | --- |
| Стартовый | Список проектов, галерея шаблонов и заданий, импорт JSON |
| Редактор (главный) | Холст, палитра, панель свойств, нижняя панель — разделы 5.1–5.12, 5.14 |
| Сравнение | Мастер запуска, прогресс и отчёт — раздел 5.13; открывается из верхней панели |
| Справочник | Короткие статьи по элементам и паттернам (уровень «если успею») |

## 5 Функциональные требования

### 5.1 Холст

- Добавление элемента перетаскиванием из палитры; перемещение, переименование, удаление (Delete), копирование и вставка.
- Связь создаётся перетаскиванием от маркера одного узла к другому. Недопустимая связь (например, БД → сервис) не создаётся, показывается причина.
- Масштаб и панорама, мини-карта, привязка к сетке, множественный выбор рамкой.
- Отмена и повтор действий (Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z), не менее 50 шагов.
- Подсветка ошибок схемы прямо на узлах: сервис без эндпоинтов, шаг ссылается на неподключённый узел, сага без брокера и т.п. Схему с ошибками запустить нельзя.

### 5.2 Элементы и их параметры

| Элемент | Основные параметры | Может связываться с |
| --- | --- | --- |
| Клиент (генератор нагрузки) | RPS, профиль нагрузки, смесь эндпоинтов в % | Gateway, балансировщик, сервис |
| API Gateway | Пул обработчиков, задержка маршрутизации, лимит RPS | Балансировщик, сервис |
| Балансировщик | Алгоритм (round robin, least connections) | Экземпляры сервиса |
| Сервис | Число экземпляров, пул обработчиков, таймауты, ретраи, эндпоинты (5.5) | Сервис, БД, кэш, брокер |
| База данных | Пул соединений, время чтения и записи (среднее и разброс), таблицы и начальные данные, уровень изоляции | Только входящие связи |
| Кэш | Емкость, TTL, доля попаданий | Только входящие связи |
| Брокер сообщений | Топики и партиции, задержка доставки, семантика (at-most-once, at-least-once), вероятность дубля | Подписчики-сервисы |

Каждый параметр имеет значение по умолчанию (из калибровки движка), единицы измерения и подсказку «что это и на что влияет».

### 5.3 Панель свойств

- Открывается справа при выборе узла или связи. Вкладки для сервиса: «Параметры», «Эндпоинты», «Метрики».
- Проверка значений при вводе (диапазоны, целые числа), кнопка «Сбросить к умолчанию».
- Во время запуска изменения параметров применяются на лету (команда `patch`). Параметры, которые нельзя менять во время работы, блокируются с пояснением.

### 5.4 Масштабирование БД

У выбранной БД есть три кнопки. Каждая операция отменяема и показывает короткое пояснение, чем она отличается от двух других.

- **Шардировать.** Диалог: число шардов (2–8), ключ шардирования, стратегия (hash, range). На холсте БД превращается в группу: маршрутизатор и N связанных узлов-шардов. Если транзакция какого-либо эндпоинта теперь затрагивает несколько шардов, показывается предупреждение и предложение выбрать паттерн (5.6).
- **Реплицировать.** Диалог: число реплик (1–5), режим (синхронная, асинхронная), задержка репликации, политика чтения (всё с лидера или чтение с реплик). На холсте появляются узлы-реплики, связанные с лидером пунктиром; на связи видно текущее отставание.
- **Партиционировать.** Диалог: таблица, ключ и число партиций. Узел остаётся одним, внутри него показываются сегменты. Пояснение: партиции снижают конкуренцию за блокировки и стоимость запроса, но не добавляют мощности сервера, в отличие от шардов.

### 5.5 Поведение сервисов (редактор эндпоинтов)

- У сервиса список эндпоинтов (имя, метод) и обработчиков сообщений (подписка на топик).
- У каждого — цепочка шагов с перетаскиванием для смены порядка. Типы шагов: чтение из БД, запись в БД, синхронный вызов сервиса, публикация в топик, чтение и запись кэша, вычисление (время CPU).
- Целевой узел шага выбирается из списка узлов, связанных с сервисом. Для шагов с данными указывается действие над данными (например, «списать amount со счёта»), чтобы движок мог проверять инварианты.
- Список действий над данными — фиксированный набор из словаря движка, а не произвольный код.

### 5.6 Транзакции и паттерны

- В цепочке шагов пользователь отмечает диапазон как одну бизнес-транзакцию и выбирает паттерн: без транзакции, локальная, 2PC, сага-оркестрация, сага-хореография, TCC.
- Опции паттерна: Transactional Outbox (вкл/выкл), идемпотентность потребителей (вкл/выкл), таймауты фаз, число ретраев. Для 2PC и саги-оркестрации выбирается узел-координатор.
- Для саги и TCC компенсирующие действия генерируются автоматически («списать» → «вернуть») и показываются рядом с шагами; можно поменять их длительность.
- При выборе транзакции на холсте подсвечиваются её участники и координатор.
- Инварианты данных выбираются из готового набора («сумма денег не меняется», «остаток ≥ 0», «оплаченный заказ зарезервирован») с указанием таблиц и полей.

### 5.7 Нагрузка

- Параметры узла «Клиент»: целевой RPS; профиль (постоянный, линейный рост, всплеск, синусоида); смесь эндпоинтов в процентах (сумма = 100%).
- Во время запуска RPS меняется ползунком прямо на узле или в панели свойств.
- На схеме может быть несколько клиентов с разными профилями.

### 5.8 Управление симуляцией

- Панель управления: «Старт», «Пауза», «Стоп», «Сброс»; скорость от ×0,1 до ×100; часы виртуального времени; поле seed.
- Во время работы разрешены: изменение параметров, шардирование и репликация, добавление экземпляров сервиса, отказы. Удаление узла с трафиком требует подтверждения: запросы к нему начнут падать.
- Каждое изменение схемы во время запуска отмечается вертикальной линией на графиках, чтобы было видно «до и после».

### 5.9 Визуализация хода симуляции

- Цвет узла по загрузке: до 70% — зелёный, 70–90% — жёлтый, выше 90% или растущая очередь — красный; отключённый узел — серый с перечёркнутым значком. Пороги настраиваются.
- Бейджи на узле: RPS, p99, длина очереди; у БД дополнительно число удерживаемых блокировок, у реплики — отставание, у брокера — непрочитанные сообщения.
- Толщина связи пропорциональна трафику.
- Точки-запросы движутся по связям (по выборке `flows`). Цвет точки задаёт вид: запрос, ответ, сообщение, компенсация, ошибка. Анимацию можно выключить.

### 5.10 Отказы (хаос)

- Контекстное меню узла: «Отключить», «Включить», «Замедлить в k раз».
- Контекстное меню связи: добавочная задержка, потеря пакетов %, дублирование %, разрыв (partition).
- Расписание отказов: список событий вида «на 30-й секунде отключить узел X на 10 с», чтобы сценарий повторялся в сравнении.
- Отказ в точке протокола: «уронить координатор 2PC после prepare», «уронить оркестратор саги после шага N».

### 5.11 Трассировка

- Список последних транзакций с фильтром по исходу: зафиксирована, откачена, скомпенсирована, зависла, нарушила инвариант.
- По клику — таймлайн в стиле Jaeger: строка на узел, отрезки работы, ожидания в очереди, удержания блокировок и компенсаций.
- Путь выбранной транзакции подсвечивается на холсте.

### 5.12 Метрики и графики

- Нижняя панель, глобальные графики за последние 60 с виртуального времени: пропускная способность; p50/p95/p99; доля успешных, откаченных и скомпенсированных транзакций; ошибки; нарушения инвариантов.
- При выборе узла — его собственные графики (вкладка «Метрики» панели свойств).
- Экспорт данных запуска в CSV.

### 5.13 Режим сравнения

1. Мастер запуска: текущая схема; транзакция, для которой перебираются паттерны; 2–5 паттернов; список уровней нагрузки; сценарий отказов; число повторов (разные seed); длительность прогона.
2. Прогресс: сколько прогонов готово из скольких, остаточное время, отмена.
3. Отчёт: таблица метрик по паттернам (среднее и разброс по повторам); графики «задержка от нагрузки» и «пропускная способность от нагрузки» по линии на паттерн; столбцы по нарушениям инвариантов, сообщениям на транзакцию, времени восстановления.
4. Экспорт отчёта: CSV с данными и PNG графиков (для вставки в текст диплома). Отчёты сохраняются и открываются повторно.

### 5.14 Подсказки и задания

- По событию `alert` рядом с узлом появляется подсказка: что происходит («БД orders перегружена, очередь 800»), почему, и кнопки действий («Добавить реплику», «Шардировать»), которые сразу применяют операцию.
- Подсказки можно выключить; история собирается в журнале событий.
- Режим заданий: задание = стартовая схема + целевые условия (например, «2000 RPS, p99 < 300 мс, 0 нарушений за 60 с»). Условия проверяются на лету и показываются чек-листом.

### 5.15 Проекты и шаблоны

- Автосохранение в браузере (IndexedDB), список проектов на стартовом экране.
- Экспорт и импорт проекта в JSON (формат 6.1) с проверкой версии формата.
- Галерея шаблонов: «Пустой проект», «Интернет-магазин» (Order → Payment → Inventory → Shipping), «Банковский перевод», «Бронирование поездки».

## 6 Взаимодействие с движком моделирования

Фронтенд обменивается с движком двумя каналами: REST для разовых операций и WebSocket для интерактивного запуска. Точный контракт фиксируется в ТЗ движка; ниже — то, что требуется от него фронтенду.

### 6.1 Формат схемы

Схема — JSON-документ с версией формата (`schemaVersion`). Он содержит:

- `nodes` — элементы: id, тип, имя, параметры, координаты на холсте, ссылка на родительскую группу (для шардов и реплик);
- `edges` — связи: откуда, куда, сетевые параметры (задержка, вероятность потери);
- `endpoints` — эндпоинты сервисов с цепочками шагов и выбранным паттерном транзакции;
- `workload` — профиль нагрузки клиентов;
- `faults` — запланированные отказы;
- `invariants` — проверяемые инварианты данных;
- `seed` — зерно случайности.

### 6.2 REST

| Метод | Назначение |
| --- | --- |
| `POST /api/validate` | Проверка схемы; ответ — список ошибок и предупреждений с id элементов |
| `GET /api/templates`, `GET /api/templates/{id}` | Список и содержимое шаблонов и заданий |
| `POST /api/experiments` | Запуск пакетного сравнения; ответ — id эксперимента |
| `GET /api/experiments/{id}` | Статус и прогресс эксперимента |
| `GET /api/experiments/{id}/report` | Агрегированные результаты и выгрузка CSV |

### 6.3 WebSocket интерактивного запуска

Команды фронтенда: `start` (схема), `pause`, `resume`, `stop`, `setSpeed`, `patch` (изменение схемы на лету), `injectFault`, `setLoad`, `getTrace` (детали одной транзакции).

Сообщения движка:

- `tick` — раз в 100–250 мс реального времени: виртуальное время и метрики по каждому узлу (RPS, очередь, загрузка, p50/p99, ошибки, блокировки);
- `flows` — выборка запросов для анимации (не все запросы, а до N в секунду): связь, направление, вид (запрос, ответ, сообщение, компенсация), исход;
- `alert` — обнаруженная проблема с кодом, id узла и параметрами для подсказки;
- `violation` — нарушение инварианта с id транзакции;
- `trace` — ответ на `getTrace`;
- `finished` / `error`.

Тексты подсказок хранятся на фронтенде по коду `alert`, чтобы движок не зависел от языка интерфейса.

## 7 Нефункциональные требования

| Требование | Значение |
| --- | --- |
| Размер схемы | До 100 узлов и 200 связей без заметных тормозов при редактировании (≥ 50 кадр/с) |
| Анимация | До 500 одновременно движущихся точек-запросов при ≥ 30 кадр/с |
| Обработка `tick` | ≤ 16 мс на сообщение, чтобы интерфейс не подвисал |
| Браузеры | Последние версии Chrome, Firefox, Safari, Edge |
| Экран | Десктоп, от 1366×768; мобильная версия не требуется |
| Язык | Русский; все строки вынесены в файлы локализации, чтобы можно было добавить английский |
| Темы | Светлая и тёмная |
| Доступность | Состояние узла передаётся не только цветом, но и значком с числом; горячие клавиши для основных действий (пробел — пуск/пауза) |
| Надёжность | Автосохранение проекта не реже раза в 10 с; при обрыве WebSocket — сообщение и попытки переподключения |
| Поставка | Статика фронтенда встраивается в Go-бинарник через `embed`: всё приложение запускается одной командой или одним Docker-контейнером |
| Авторизация | Не требуется: локальное однопользовательское приложение |
| Качество кода | ESLint + Prettier, строгий режим TypeScript, юнит-тесты для хранилища и преобразований схемы |

## 8 Приоритеты и границы

MVP — то, без чего диплом не защитить: сборка схемы, запуск, видимые проблемы и сравнение паттернов. Всё остальное добавляется после того, как MVP работает целиком.

| Уровень | Что входит |
| --- | --- |
| MVP (обязательно) | Холст (5.1); клиент, сервис, БД, брокер (5.2); панель свойств (5.3); шардирование и репликация (5.4); редактор эндпоинтов (5.5); паттерны 2PC и обе саги + инварианты (5.6); постоянная нагрузка (5.7); управление запуском (5.8); цвет и бейджи узлов (5.9); отключение узла и задержка связи (5.10); глобальные графики (5.12); базовое сравнение с таблицей и графиками (5.13); сохранение, импорт/экспорт JSON, один шаблон «Интернет-магазин» (5.15) |
| Желательно | Анимация запросов по связям; TCC, Outbox и переключатель идемпотентности; трассировка (5.11); фильтры отказов связи и отказы по расписанию; партиционирование; Gateway, балансировщик, кэш; подсказки (5.14); профили нагрузки ramp/spike |
| Если успею | Режим заданий; встроенный справочник; ещё два шаблона; тёмная тема; экспорт холста в PNG; запуск движка в браузере через WASM |

### Вне рамок

- Многопользовательская работа, аккаунты, совместное редактирование.
- Развёртывание собранной схемы в реальные контейнеры и генерация кода сервисов.
- Произвольная бизнес-логика на языке программирования внутри сервисов.
- Мобильная версия.

## 9 Открытые вопросы и критерии приёмки

### Открытые вопросы

- [ ] Подход: имитационная модель или реальные сервисы — согласовать с руководителем.
- [ ] Входит ли TCC в MVP или достаточно 2PC и двух саг?
- [ ] Нужны ли пользовательские инварианты или хватит готового набора?
- [ ] Нужен ли режим заданий для защиты, или он только приятный бонус?
- [ ] Где работает движок: на сервере (WebSocket) или в браузере (WASM)? По умолчанию — на сервере.
- [ ] Требования кафедры к оформлению ТЗ: нужен ли перевод в структуру ГОСТ 34.602 или 19.201?

### Критерии приёмки

1. Все пять сценариев из раздела 2 проходятся целиком в интерфейсе и покрыты e2e-тестами.
2. Одна и та же схема с одним seed даёт одинаковые цифры в отчёте сравнения.
3. Экспорт и повторный импорт проекта дают идентичную схему.
4. Показатели производительности из раздела 7 подтверждены замером на схеме из 100 узлов.
5. Приложение запускается на чистой машине одной командой.
