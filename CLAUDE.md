# Среда моделирования распределённых транзакций — фронтенд

Дипломный проект: веб-песочница, где пользователь собирает микросервисную систему на холсте
(сервисы, БД, брокеры, кэш, балансировщики), запускает её имитационную модель под нагрузкой
и видит последствия архитектурных решений и паттернов распределённых транзакций
(2PC, сага-оркестрация, сага-хореография, TCC, Outbox).

## Источники требований

- `docs/frontend-spec.md` — ТЗ фронтенда. Это главный источник требований: перед любой задачей
  сверяйся с нужным разделом и ссылайся на номера пунктов (например, «5.4»).
- Приоритеты — раздел 8 ТЗ. Сначала делаем только MVP, «желательно» — после того, как MVP работает целиком.

## Архитектура (кратко)

- Фронтенд не моделирует систему сам. Он редактирует схему (JSON, формат — раздел 6.1 ТЗ),
  отправляет её движку и отображает поток событий.
- Движок — отдельный Go-сервер (пишется позже). Связь: REST (раздел 6.2) + WebSocket (раздел 6.3).
- Пока движка нет, фронтенд работает с **mock-движком**: `src/engine/mock/` генерирует
  правдоподобные `tick`, `flows`, `alert`, `violation` по текущей схеме (простая модель очередей:
  загрузка = входящий RPS / ёмкость узла). Переключение mock/реальный движок — через переменную
  окружения `VITE_ENGINE=mock|ws`.
- Весь обмен с движком идёт через один интерфейс `EngineClient` (`src/engine/types.ts`),
  у которого две реализации: mock и WebSocket. Компоненты UI не знают, какая из них активна.

## Стек

TypeScript (strict), React, Vite, React Flow (`@xyflow/react`), Zustand, Apache ECharts,
shadcn/ui + Tailwind CSS, Zod, Vitest, Playwright. Новые зависимости — только если без них никак,
и с объяснением зачем.

## Структура

```
src/
  app/            маршруты, раскладка экранов
  canvas/         холст, кастомные узлы и связи, слой анимации (Canvas 2D)
  panels/         палитра, панель свойств, нижняя панель
  features/       scaling (шард/реплика/партиция), endpoints, transactions, chaos,
                  tracing, metrics, compare, hints, projects
  engine/         types.ts (контракт), mock/, ws/
  schema/         типы схемы, Zod-схемы, преобразования, валидация
  store/          Zustand-хранилища
  i18n/           строки интерфейса (ru)
```

## Правила

- Язык интерфейса — русский; все строки только через `src/i18n/`, без хардкода в компонентах.
- Типы схемы и сообщений движка — в одном месте (`src/schema`, `src/engine/types.ts`).
- Логику (преобразования схемы, шардирование, валидация) держать в чистых функциях
  и покрывать юнит-тестами Vitest.
- Работать маленькими шагами: одна фича из ТЗ → проверка (`npm run build`, `npm test`) → коммит.
- Перед большой задачей сначала показать план и дождаться подтверждения.

## Команды

- `npm run dev` — дев-сервер
- `npm run build` — сборка
- `npm test` — юнит-тесты
- `npm run e2e` — e2e-тесты Playwright
